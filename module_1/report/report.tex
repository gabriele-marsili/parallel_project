\section{Design Choices}
% ===========================================================================

Given $N$ keys (\texttt{uint64\_t}) and $P$ partitions (power of two), the task is to compute $\text{part\_id}[i] = h(\text{keys}[i]) \in [0,P)$ for every key.

\subsection{Mapping Function}

I chose a Fibonacci multiply-shift hash operating on 32~bits:
$$h(k) = \bigl((k_\text{lo} \oplus k_\text{hi}) \cdot A_{32}\bigr) \gg (32 - \log_2 P)$$
where $A_{32} = \texttt{0x9E3779B9} = \lfloor 2^{32}/\varphi \rfloor$~\cite{knuth1998}.
This is an instance of the \emph{hashing by multiplication} scheme described in~\cite{ferragina2023} (\S\,8.2), where the golden-ratio constant $A = (\sqrt{5}-1)/2 \approx 0.618$ is suggested for its bit-spreading properties. The right-shift extraction follows the \emph{multiply-add-shift} universal hash family of~\cite{ferragina2023} (\S\,8.3): $h_{a,b}(k)=(ak+b \bmod 2^w) \operatorname{div} 2^{w-\ell}$, here simplified with $b\!=\!0$ and the Fibonacci constant as~$a$.

The XOR of the two 32-bit halves preserves information from both halves before the multiplication. The Fibonacci constant spreads bits well across the output range, and measured distribution on $10^8$ keys with $P\!=\!256$ gives $\max(\text{count})/\text{expected} = 1.005$.

The main reason for working in 32~bits is SIMD compatibility: \texttt{\_mm256\_mullo\_epi32} (\texttt{vpmulld}) is a single native AVX2 instruction that multiplies 8~uint32 values at once. A~64-bit multiply in AVX2 would need 3~\texttt{vpmuludq} instructions plus shifts and adds per element, which I verified to be slower than the scalar baseline in this bandwidth-limited regime.

\subsection{Data Layout and P}

Keys and output partition IDs are in separate contiguous arrays with unit stride---the layout most amenable to vectorization. Memory is 32-byte aligned via \texttt{posix\_memalign} for AVX2 aligned loads. $P$ is a power of two so that modulo reduces to a right-shift.

% ===========================================================================
\section{Auto-vectorization}
% ===========================================================================

The plain C++ kernel is compiled from a single source file into two binaries: one with \texttt{-fno-tree-vectorize} (baseline), one with \texttt{-O3 -march=native -mavx2 -ftree-vectorize} (autovec). Both use \texttt{-fopt-info-vec-optimized} and \texttt{-fopt-info-vec-missed} for diagnostics.

GCC~12.2 reports successful vectorization of the kernel loop. The relevant lines from the full report (file \texttt{vec\_report\_optimized.txt}, included in the deliverables):

\begin{lstlisting}
src/plain.cpp:33:26: optimized: loop vectorized
  using 32 byte vectors
src/plain.cpp:33:26: optimized: loop vectorized
  using 16 byte vectors
include/common.hpp:77:27: optimized: loop vectorized
  using 32 byte vectors
include/common.hpp:264:19: optimized: loop vectorized
  using 32 byte vectors
\end{lstlisting}

GCC emits two versions of the kernel loop: one using 256-bit AVX2 registers (\texttt{ymm}, 32-byte vectors, 8~uint32 per instruction) and one using 128-bit SSE registers (\texttt{xmm}, 16-byte vectors, 4~uint32 per instruction). At runtime the 256-bit path is taken when AVX2 is available; the 128-bit version serves as a fallback on older hardware. The \texttt{common.hpp} lines correspond to the checksum and key generation loops, which GCC also vectorizes. The \texttt{-fopt-info-vec-missed} report was empty---GCC found no loop that it attempted but failed to vectorize.

The loop satisfies all conditions: known trip count, no loop-carried dependencies, no function calls in the body, \texttt{\_\_restrict\_\_} to exclude aliasing, and unit stride access.

% ===========================================================================
\section{AVX2 Intrinsics}
% ===========================================================================

The hand-written version processes 8~keys per iteration. Two \texttt{ymm} loads bring in 4+4~uint64 keys. Each key is XOR-folded by shifting right 32~bits and XORing with the original value, leaving the folded result in the low 32~bits of each 64-bit lane. The 8~folded values are then packed into a single \texttt{ymm} register: \texttt{permutevar8x32} with indices \texttt{[0,2,4,6,1,3,5,7]} extracts the low-32 values from each register, and \texttt{permute2x128} with selector \texttt{0x20} combines the lower 128~bits of both into one register of 8$\times$uint32. A single \texttt{vpmulld} performs all 8~Fibonacci multiplications, a right-shift extracts partition IDs, and a 256-bit store writes the results. The remaining $N \bmod 8$ keys are handled by a scalar tail.

The AVX2 binary verifies correctness against an internal scalar reference (compiled with \texttt{-fno-tree-vectorize} via pragma) by comparing FNV-1a checksums before benchmarking; for $N\!\leq\!32$ it also prints element-wise comparison.

At $N\!=\!10^8$ the CUDA kernel alone reaches 67\,320~Mkeys/s (808~GB/s, 81\% of A30 HBM2 peak), but end-to-end including PCIe transfers is only 1\,031~Mkeys/s ($1.12\times$); see Section~\ref{sec:cuda}.

\subsection{Why the Speedup is Limited}

Each key needs 12~bytes of memory traffic (8\,B read + 4\,B write) and only $\sim$4 integer operations. The operational intensity is $I = 4/12 \approx 0.33$ ops/byte, placing the kernel in the bandwidth-bound region of the roofline. The single-core bandwidth on node09 was measured at $\sim$16.4~GB/s; the autovec version reaches 15.7~GB/s, about 96\% of this ceiling (Figure~\ref{fig:roofline}). SIMD speeds up the compute part, but memory transfers---which dominate---stay the same; the 1.43$\times$ speedup comes from more efficient bandwidth utilization, not faster computation.

\subsection{Autovec vs.\ AVX2 Intrinsics}

Somewhat counterintuitively, the compiler-vectorized version outperforms the hand-written intrinsics (15.7 vs 14.4~GB/s). Since the kernel is bottlenecked by memory, the marginal differences in instruction scheduling, loop unrolling, and register allocation that GCC applies during auto-vectorization translate into slightly better bandwidth utilization. The intrinsics code imposes a rigid instruction sequence that the compiler cannot easily rearrange.

\subsection{Parameter Sweeps}

\textbf{N-sweep} (Figure~\ref{fig:speedup}): speedup is stable across all input sizes, from $10^6$ to $2{\times}10^8$ keys. This confirms that the kernel is bandwidth-bound regardless of $N$.

\textbf{P-sweep} (Figure~\ref{fig:sweeps}a): throughput and speedup are independent of $P$ (all curves flat across $P \in [2, 1024]$), confirming that changing $P$ only modifies the shift constant---memory traffic and compute per key are unchanged.

\textbf{Key-space sweep} (Figure~\ref{fig:sweeps}b): throughput is invariant to key-space size (duplicate rate), as expected for a branchless hash with constant cost per key.

\subsection{Measurement Stability}

All 55 measurement points have a coefficient of variation below 5\%. The autovec binary is the most stable (mean CoV~0.4\%), while AVX2 intrinsics show slightly more variance (mean CoV~3.5\%), likely because GCC's scheduling produces more deterministic memory access patterns than the hand-written sequence.

% ===========================================================================
\section{Conclusions}
% ===========================================================================

This kernel is a textbook memory-bound workload. At $I\!=\!0.33$ ops/byte, performance is dictated by DRAM bandwidth regardless of the SIMD strategy. The autovec version reaches 96\% of the single-core bandwidth ceiling, leaving practically no room for single-thread improvement. The choice of a 32-bit hash (native \texttt{vpmulld}) over a 64-bit one was critical: with a 64-bit hash, AVX2 was actually slower than scalar due to the \texttt{vpmuludq} decomposition overhead in a bandwidth-limited regime.
