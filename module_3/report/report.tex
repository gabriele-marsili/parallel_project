\section{Introduction}
%---------------------------------------------------------------
This report describes the OpenMP implementation of the partitioned
hash join developed in Module~2. The algorithm is unchanged: $R$ and
$S$ are partitioned through a common key mapping and a local join is
performed independently on each partition. The objective of the study
is to assess which OpenMP constructs are appropriate for this kernel
under both balanced and skewed workloads, and to compare the resulting
performance with the \texttt{std::thread} implementation of Module~2.

Two parallel variants were developed. They share the same
three-phase structure, the same hash-table layout and the same
mapping function, but each phase is parallelised end-to-end with a
different OpenMP construct: the loop variant uses worksharing
\texttt{parallel for} loops throughout, the task variant emits
explicit \texttt{omp task} blocks (with Longest Processing Time
First ordering on the join). Keeping the construct consistent across
phases isolates the cost of the construct itself, rather than mixing
two parallelism models inside the same run. All experiments were
carried out on a node of the SPM cluster.

%---------------------------------------------------------------
\section{Algorithm and OpenMP Strategies}
%---------------------------------------------------------------

\subsection{Three-phase Structure}
Given relations $R$ and $S$ of size $N_R$ and $N_S$, each tuple
carries a key $k$ which is mapped to partition $p = k \bmod P$ with
$P=128$. Since $P$ is a power of two, the equivalent bitmask form
$k\,\&\,(P-1)$ is used. Each relation is processed in three phases:

\begin{enumerate}
  \item \textbf{Histogram} -- count tuples per partition.
  \item \textbf{Scatter} -- compute exclusive prefix-sum offsets and
        write tuples into contiguous per-partition buffers.
  \item \textbf{Join} -- on each partition $p$, build a hash table on
        $R_p$ and probe it with the tuples of $S_p$.
\end{enumerate}

The per-partition hash table is the \texttt{FlatCountMap} carried
over from Module~2: open-addressing with linear probing,
count-at-build, multiplicity accumulation at probe time. Its
capacity is set to the smallest power of two $\ge 2\,|R_p|$, which
keeps the load factor below $50\%$ and bounds the expected probe
length to a small constant.

\subsection{Loop-level Variant}
The loop variant follows the canonical \texttt{parallel for} pattern.
Each thread maintains a private histogram in a 64-byte aligned
buffer; the merge into the global histogram and the exclusive prefix
sum are executed by a single thread inside an
\texttt{\#pragma omp single} block. The scatter phase is a
\texttt{parallel for} with \texttt{schedule(static)}, since the
per-tuple work is constant. The join phase is then expressed as

\small\begin{verbatim}
#pragma omp parallel for schedule(dynamic,1) \
    default(none) shared(P, Rpart, Spart)    \
    reduction(+: join_count, checksum1, checksum2)
for (uint32_t pid = 0; pid < P; ++pid) {
    JoinResult r = join_one_partition(Rpart, Spart, pid);
    join_count += r.join_count;
    checksum1  += r.checksum1;
    checksum2  += r.checksum2;
}
\end{verbatim}\normalsize

The choice of \texttt{dynamic,1} addresses the irregular
per-iteration cost. Under the skew of Section~\ref{sec:skew} a hot
partition holds $\approx 22.6\%$ of the records and a cold one
$\approx 0.078\%$, a ratio of $\sim 290\times$ in per-partition
work, so any static distribution leaves the thread that picks up
the heavy partitions on the critical path. The runtime dispatch of \texttt{dynamic,1} hands out
one partition at a time and lets an idle thread grab a cold
partition while the hot ones are still in flight; its overhead is
small at the granularity of a partition, since the sweep of
Section~\ref{sec:schedule} shows all policies within $1\%$ on
uniform input, where the imbalance penalty disappears. The
\texttt{reduction(+:\dots)} clause covers the three
\texttt{uint64\_t} scalars that accumulate the result.

\subsection{Task Variant with LPT}\label{sec:task}
In the task variant histogram and scatter are emitted as $T$
explicit tasks per phase, one per chunk
$[(N\!\cdot\!t)/T,\;(N\!\cdot\!(t{+}1))/T)$, which reproduces the
distribution of \texttt{schedule(static)} but goes through the task
queue: on a regular workload the variant pays the task-creation
overhead with no balancing benefit, and the comparison surfaces it. Each task captures its index $t$ and
addresses the per-task slot \texttt{local\_hists[t]} (histogram) or
\texttt{cursors[t]} (scatter), so the offsets remain consistent
regardless of which thread the runtime picks up the task on. Two
\texttt{taskgroup} blocks bracket histogram and scatter so that the
sequential merge only starts once every count has landed. The join
is expressed as an explicit task loop:

\small\begin{verbatim}
#pragma omp parallel default(none) \
    shared(P, order, Rpart, Spart, thr_results, ...)
{
  #pragma omp single nowait
  for (uint32_t idx = 0; idx < P; ++idx) {
    uint32_t pid = order[idx];  // LPT order
    #pragma omp task firstprivate(pid) \
        shared(Rpart, Spart, thr_results)
    { /* cold: build+probe; hot: probe split
         into a nested taskgroup (Sec. 2.4) */ }
  }
}
\end{verbatim}\normalsize

The \texttt{nowait} clause is required: without it the $T-1$ workers
would wait at the implicit barrier of \texttt{single} until task
emission completes, instead of consuming tasks while the master is
still creating them.

The \texttt{order} array drives the scheduling. Partitions are sorted
by decreasing $|R_p| + |S_p|$ before submission, which is the Longest
Processing Time First (LPT) heuristic\,\footnote{R.~L.~Graham,
\emph{Bounds on multiprocessing timing anomalies}, SIAM
J.~Appl.~Math.\ 17(2):416--429, 1969; LPT is shown to achieve
makespan within $4/3 - 1/(3m)$ of the optimum on $m$ machines.},
a classical greedy for makespan minimisation when
independent tasks of variable size are dispatched to identical
workers. On this problem ($P{=}128$,
$T\!\le\!32$) it has two practical effects: heavy partitions enter
the queue first and are therefore unlikely to land on the critical
path at the end of the run, while small partitions remain available
to fill the gaps left by the heavy ones. The sum $|R_p|+|S_p|$ is an
appropriate cost proxy because the per-partition cost is linear in
the size of its two inputs.

All tasks are tied (the OpenMP default). Each body reads
\texttt{omp\_get\_thread\_num()} once and uses the returned index
locally to write into \texttt{thr\_results}; no task scheduling
point separates the read from its use, so the index is stable
under tied semantics without further care, and untied would offer
no advantage at the granularity of these tasks.

The reduction uses a manually padded array
\texttt{PaddedResult thr\_results[T]}, declared with
\texttt{alignas(64)} and validated by a \texttt{static\_assert}, so
per-thread slots sit on distinct cache lines and false sharing is
removed. Synchronisation between phases differs by variant: the loop
variant relies on the implicit barriers of the worksharing
constructs; the task variant on the implicit \texttt{taskwait} of
its two \texttt{taskgroup} blocks.

\subsection{Targeted Optimisations}\label{sec:opt}
Three additional optimisations were applied on top of the baseline
strategy described above. They follow directly from the cost model of
the kernel and from the structural bound observed on skewed input.

\paragraph{Software prefetching in scatter and probe.}
Both loops have a sequential read stream, which the hardware
prefetcher covers, and a random-access stream, which it does not.
Two \texttt{\_\_builtin\_prefetch} calls mask the miss latency on
the random side: in the scatter, the destination slot
\texttt{part.data[cursors[tid][pid\_next]]} is prefetched 12
iterations ahead; in the probe, the hash slot
\texttt{tbl.slots[slot\_of(k\_next)]} is prefetched 8 iterations
ahead. The distances leave enough work between prefetch and use to
cover the L1$\to$L2 latency in the scatter and the L2$\to$L3
latency in the heavier probe iteration.

\paragraph{Intra-partition parallelism for hot partitions.}
The asymptotic skewed efficiency $\le H/T$ is a structural bound: no
external scheduling, including LPT, can extract more parallelism than
the number of heavy partitions $H$. The bound is broken by exposing
parallelism \emph{within} a hot partition. The build phase still runs
sequentially because concurrent updates on \texttt{FlatCountMap} would
require atomic counters, but the probe is read-only on the table and
parallelises naturally. A partition is classified as hot when its
weight $|R_p| + |S_p|$ exceeds eight times the average $\bar{w}$;
its probe is split into $K = \min(T, \lfloor w/\bar{w}\rfloor)$
sub-tasks (with a lower clamp to $2$). The sub-tasks are
emitted inside a \texttt{taskgroup} so that the shared table outlives
all readers. The probe of each hot partition can therefore be served
by up to $T$ cooperating threads, which is what restores the
parallelism that LPT alone could not extract.

\paragraph{NUMA placement of partition buffers (attempted).}
A parallel \texttt{schedule(static)} zero-init on the partition
buffers was added to spread their pages across the two NUMA nodes
via Linux first-touch. The step is a no-op as written:
\texttt{Record} has an in-class \texttt{key\{\}} initialiser, so
\texttt{vector::resize} already touches every page on the calling
thread, pinning the buffers to one NUMA node. A correct fix needs
an uninitialised allocator; this is a known limitation.

%---------------------------------------------------------------
\section{Skewed Workload}\label{sec:skew}
%---------------------------------------------------------------
The skewed dataset is produced by a Bernoulli mixture model. With
probability $\rho=0.9$ the next key is sampled from a hot pool of
$H=4$ keys, chosen so that they fall on four distinct partitions;
with probability $1-\rho=0.1$ the key is drawn uniformly from
$[0,\textit{max\_key})$. With $(\rho{=}0.9, H{=}4)$ the model concentrates $90\%$ of the
probes on only $4$ partitions out of $128$; the hot-to-cold ratio
is then a structural consequence of the choice rather than a
tuning knob. The expected fraction of records assigned to a
single hot partition is
\[
  f_{\text{hot}} = \frac{\rho}{H} + \frac{1-\rho}{P}
                 = \frac{0.9}{4} + \frac{0.1}{128}
                 \approx 0.226,
\]
while a cold partition receives $f_{\text{cold}}\approx 0.00078$. The
two values are a direct consequence of the choice of $(\rho,H,P)$
and produce the order-of-magnitude gap between hot and cold
partitions that the experiments below probe.

The generator is driven by a \texttt{splitmix64} RNG with the seed
exposed on the command line, which makes runs reproducible
bit-by-bit. The \texttt{hot\_count} parameter is clamped to $P$ to
prevent a non-terminating loop in the case where more hot partitions
are requested than exist.

\section{Validation}
%---------------------------------------------------------------
Two complementary mechanisms are used. For small inputs
($N_R, N_S \le 500$) both \texttt{hashjoin\_seq} and
\texttt{hashjoin\_omp} run an in-process \emph{naive} $O(|R|\cdot|S|)$
verifier (\texttt{include/verifier.hpp}) that performs a double loop
over all pairs and emits a \texttt{naive\_verify=PASS} line when the
triple matches the algorithm's output; the verifier is invoked
\emph{outside} the timed region. For larger inputs the script
\texttt{scripts/validate.sh} sweeps modes $\times$ workloads
$\times$ thread counts $\in\{1,2,4,8,16\}$ at $N_R{=}10^6$,
$N_S{=}2{\cdot}10^6$. The validation range stops at $T{=}16$ since
the SMT points only re-exercise the same code paths; they are kept
for the performance evaluation, which spans
$T\!\in\!\{1,2,4,8,16,20,32\}$. The script compares the triple
$(\text{join\_count},\text{checksum}_1,\text{checksum}_2)$ against a
reference: the sequential baseline for uniform input and the
parallel run at $T=1$ in the same mode for skewed input (the
sequential implementation does not generate skewed data). As an
additional check, the loop and task variants at $T=4$ are required to
produce identical triples on the same input.

The checksums are constructed to be invariant under task ordering:
each match contributes $\texttt{splitmix64}(k)\cdot m$ added modulo
$2^{64}$, so the total is independent of the order in which tasks
complete. All combinations pass on the cluster.

\section{Experimental Evaluation}
%---------------------------------------------------------------

\subsection{Setup}
All experiments are run on a single compute node of
\textit{spmcluster}, allocated through SLURM with
\texttt{--exclusive} and \texttt{--cpus-per-task=32}: dual-socket
Intel Xeon E5-2640~v2 at 2.00~GHz, 8 cores per socket, 2 hardware
threads per core (32 logical CPUs over 16 physical cores), 128~GB
RAM, two NUMA nodes. The same hardware and SLURM allocation policy
were used for the Module~2 measurements reported in
Section~\ref{sec:m2cmp}, so the cross-module comparison is
apples-to-apples. No multi-node or distributed execution is used.
The build uses GCC with OpenMP~4.5 and \texttt{-O3 -march=native},
compiled on the compute node so the native ISA matches the
execution target. Unless stated otherwise, the parameters
are $N_R = 10^7$, $N_S = 2\cdot 10^7$, $P=128$, seed $42$, with each
cell averaged over three repetitions. Affinity is fixed via
\texttt{OMP\_PROC\_BIND=close} and \texttt{OMP\_PLACES=cores}.

On uniform input the task variant is slower than the loop by up to
$27\%$ at physical saturation ($0.075$~s vs $0.095$~s at $T{=}16$),
with the gap narrowing in the SMT range. The breakdown of
Section~\ref{sec:break} localises the overhead in histogram and
scatter: the per-tuple cost is regular and the task model adds
dispatch and per-task allocation work that the worksharing
\texttt{for}-loop does not pay, while on the join the two variants
stay within noise. The loop speedup grows up to $T{=}16$
($\sim 7.5\times$, efficiency $47\%$), degrades at $T{=}20$ where
the team straddles physical and SMT cores, and partly recovers at
$T{=}32$ where the kernel is already bandwidth-bound. With
$T_{\text{seq}}{=}0.802$~s (Table~\ref{tab:m2}), the absolute
speedup at $T{=}16$ is $10.69\times$ for the loop variant and
$8.42\times$ for the task variant.

On skewed input the picture inverts (Figure~\ref{fig:skewgap}). At
$T=4$ the task variant completes in $0.147$~s against $0.167$~s for
the loop, a $\sim 14\%$ advantage from LPT submission of the heavy
partitions. The gap peaks at $T=8$ ($0.094$~s vs $0.110$~s,
$\sim 18\%$) as the intra-partition split engages and narrows to
$\sim 10\%$ at $T=16$ (physical saturation): the join phase at
$T=16$ runs in $60.1$~ms for the task variant against $73.2$~ms for
the loop, a $\sim 18\%$ reduction on the dominant phase. The
hot-partition split (Section~\ref{sec:opt}) lets up to four cooperating
threads work inside each hot partition, which bypasses the $H/T$
ceiling. The efficiency at $T=16$ on skewed input is $\sim 34\%$ for
the task variant against $\sim 31\%$ for the loop; the loop stays
close to the ceiling because no external scheduling can manufacture
parallelism between independent partitions when only four of them
carry the load.

\subsection{Weak Scaling}
$N_R$ scales proportionally with $T$, with $2{\cdot}10^6$ tuples per
thread (Figure~\ref{fig:weak}).

\begin{figure}[t]
\centering
\includegraphics[width=\columnwidth]{fig_weak.pdf}
\caption{Weak scaling. Efficiency is $T(1)/T(p)$ with the input scaled
linearly with the thread count.}
\label{fig:weak}

Uniform weak scaling holds within one socket: from $T{=}1$ to
$T{=}8$ the loop variant grows from $0.132$~s to $0.166$~s
(eff.\ $\sim 79\%$) and the task variant from $0.131$~s to
$0.192$~s ($\sim 68\%$, with the gap absorbing the per-phase
task-creation cost). Once both
sockets are engaged the efficiency of the loop variant drops to
$\sim 59\%$ at $T=16$, $33\%$ at $T=20$, and $25\%$ at $T=32$; the
task variant follows a similar curve, $43\%$, $31\%$, $24\%$. The
dominant factor is memory bandwidth: the scatter phase reads and
writes a working set that grows linearly with $T$, and the
dual-socket aggregate bandwidth saturates before the core count
does. Skewed weak scaling degrades more sharply because increasing
$N_R$ also scales the load on the hot partitions in proportion; the
intra-partition split mitigates this on the probe but cannot
eliminate the sequential cost of the per-partition build. Skewed
efficiency at $T=16$ is approximately $23\%$ for the loop variant
and $33\%$ for the task variant.

\subsection{Phase Breakdown}\label{sec:break}
The breakdown in Figure~\ref{fig:breakdown} reflects the
memory-bound nature of the kernel and surfaces the loop-vs-task
trade-off at the phase level. Under uniform input the join is the
dominant phase of the loop variant ($\sim 66\%$ of the total at
$T{=}8$, $\sim 57\%$ at $T{=}16$, $\sim 51\%$ at $T{=}20$). The task
variant compresses the join share to $43$--$58\%$ across the same
range because histogram and scatter pay the per-task dispatch cost;
at $T{=}8$ uniform the task histogram takes $14$~ms against $9$~ms
for the loop, while the join is roughly identical at $\sim 73$~ms.
Under skewed input the imbalance is on the join: histogram and
scatter scale similarly between the two variants because their
per-tuple work does not depend on the partition distribution. At
$T{=}16$ skewed the join accounts for $\sim 71\%$ of the total in
the loop variant and $\sim 64\%$ in the task variant; at $T{=}20$
the gap is similar ($68\%$ vs $62\%$), reflecting the redistribution
of probe load across threads inside each hot partition. The
breakdown is not extended to $T{=}32$ because the SMT regime is
already covered in the strong and weak scaling figures.

\subsection{Schedule Sensitivity}\label{sec:schedule}
Figure~\ref{fig:schedule} shows the join time at $T=8$ for five
schedule policies on both workloads. On uniform input all policies
fall within $\sim 1\%$ of each other: with $P/T=16$ every thread
gets the same per-tuple workload regardless of how partitions are
distributed. On skewed input \texttt{static}, \texttt{static,1} and
\texttt{guided,1} cluster around $130$~ms on the join while the two
\texttt{dynamic} policies drop to $\sim 80$~ms, a $\sim 38\%$
reduction: \texttt{static} assigns the four hot partitions to
whichever threads own their iteration range and the thread that
draws all the heavy work becomes the critical path, whereas
\texttt{dynamic} reassigns partitions on demand and lets idle threads
steal from the heavy ones. \texttt{dynamic,4} and \texttt{dynamic,1}
are within noise, so the smaller chunk size has no measurable cost
at this granularity.

\centering

The skewed result confirms the choice of \texttt{dynamic,1} as the
default: under skew it is the only schedule among the five that does
not pay a $\sim 60$~ms penalty on the heavy partitions, and on
uniform input it ties with the others, so it is never worse than the
alternatives across the regimes observed.

the sequential merge of the per-thread histograms before the team
proceeds together. Algorithm, input and node are identical to
Module~3 (same SLURM allocation policy, same E5-2640~v2 hardware),
so the comparison isolates the synchronisation model and the
optimisations of Section~\ref{sec:opt}.

Both OpenMP variants outperform the \texttt{std::thread} version up
to physical-core saturation, after which Module~2 catches up and at
$T{=}32$ matches the loop variant. At $T{=}8$ the loop variant is
$\sim 1.54\times$ faster than Module~2 and the task variant
$\sim 1.35\times$; at $T{=}16$ the gap is $1.36\times$ for loop
($0.075$~s vs $0.102$~s) and $1.07\times$ for task. Two phases
account for most of the absolute gap. The first is the scatter: at
$T{=}8$ the combined scatter $R{+}S$ takes $\sim 29$~ms in the loop
variant against $\sim 85$~ms in Module~2, a difference of
$\sim 56$~ms attributable to the software prefetch on the
random-access destination slot. The second is the histogram: at
$T{=}8$ it takes $\sim 9$~ms in the loop variant against
$\sim 35$~ms in Module~2, where the \texttt{std::barrier}
completion function serialises the histogram merge while the OpenMP
loop variant performs the same merge in an \texttt{omp single} block
whose cost is partly hidden by the next worksharing region.

The behaviour at and beyond physical saturation differs. The loop
variant peaks at $T{=}16$ ($10.69\times$, efficiency $\sim 67\%$)
and then loses ground: at $T{=}20$ the team straddles physical and
SMT cores and the speedup falls to $8.35\times$, recovering only
partially at $T{=}32$ ($9.01\times$). Module~2 keeps improving with
SMT, from $7.86\times$ at $T{=}16$ to $9.01\times$ at $T{=}32$,
because its barrier overhead is amortised over a larger team. The
two implementations meet at $T{=}32$, where memory bandwidth is the
binding constraint and the synchronisation primitive becomes
second-order.

The loop variant sits above unity for $T{\le}4$ ($\text{eff}\!\approx\!1.22$
at $T{=}4$), which is not genuine super-linear scaling: the
optimisations of Section~\ref{sec:opt} are present in the parallel
binary but not in \texttt{hashjoin\_seq}, so already at $T{=}1$ the
OpenMP run is $\sim 1.44\times$ faster than the sequential baseline
(Table~\ref{tab:m2}). The numerator of the efficiency therefore
carries a constant offset that decays as $T$ grows and the
synchronisation cost takes over. The task variant shows the same
pattern but with a smaller offset because the task overhead on
histogram and scatter consumes part of the gain
($\text{eff}\!\approx\!1.12$ at $T{=}4$).


%---------------------------------------------------------------
\section{Discussion}
%---------------------------------------------------------------
On uniform input the loop variant is the better choice: its
worksharing for-loops carry no task overhead on the regular phases,
and the residual gap with the task variant grows with $T$, from
$\sim 10\%$ at $T{=}4$ to $\sim 27\%$ at $T{=}16$. On skewed input
the picture inverts: the task variant is faster from $T{=}4$
onwards, with an advantage that peaks at $\sim 18\%$ at $T{=}8$ as
the intra-partition split engages and narrows to $\sim 10\%$ at
physical saturation. The schedule-policy study shows that on
uniform input all five policies fall within $\sim 1\%$, but on
skewed input \texttt{dynamic} is $\sim 38\%$ faster than
\texttt{static} and \texttt{guided}, which is what justifies
\texttt{dynamic,1} as the default. Up to physical-core saturation
both OpenMP variants outperform the Module~2 \texttt{std::thread}
version against the shared sequential baseline: at $T{=}16$ the
loop variant reaches $10.69\times$ speedup and the task variant
$8.44\times$, against $7.86\times$ for Module~2; at $T{=}32$ the
three implementations converge ($9.01$, $8.44$ and $9.01\times$
respectively) as memory bandwidth becomes the binding constraint.
